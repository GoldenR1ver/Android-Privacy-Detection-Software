# 安卓隐私检测程序开发计划（Lab4 落地版）

## 1. 任务理解与目标

你当前已经有一条实验性管线（`oldsrc`），覆盖了：
- 隐私政策文本读取与句子级分类（知情权、决定权、访问权、修改权、删除权）
- 聚类分析
- 权限/路径判断
- 基于 Appium + MuMu 的动态执行
- LLM（`deepseek-chat`）参与大量判断

本次目标是**完全弃用 `oldsrc`，在 `src` 下重建一条可复现、可解释、可批量跑 >=10 个 APP** 的工程化工具，并对齐 Lab4 的三项核心评估：
- Lab4-1：知情权真实性（声明 vs 实际获取）
- Lab4-2：同意权真实性（关闭是否真的生效）
- Lab4-3：访问权真实性（副本完整性 + 实际采集与传输）

---

## 2. 可行性评估（结论：可行，建议全新分层重构）

## 2.1 现有方案可借鉴程度（不复用代码）

- **可复用的是“设计思想”，不是实现代码**
  - 保留流程思想：政策声明 -> 静态证据 -> 动态证据 -> 比对判定 -> 报告
  - 保留输出思想：按 APP 生成结构化结果与证据包
- **全部代码在 `src` 重写**
  - 避免旧代码中的实验性依赖与耦合关系继续扩散
  - 统一命名、统一数据结构、统一 CLI，降低后期维护成本

## 2.2 与开源组件结合的可行性

- **Exodus**：适合做 APK 初筛（权限、tracker、SDK 风险）  
  可行，接入成本低，适合作为“风险候选生成器”
- **Androguard**：适合做静态 API/调用证据提取  
  可行，能给出比 LLM 更稳定的“代码证据”
- **Frida（含 hooks 模板）**：适合做运行时取证  
  可行，但要控制范围（先覆盖 IMEI、位置、Android ID、剪贴板等高价值信息）

## 2.3 与 Lab4 要求匹配度

- **匹配度高**：实验强调“逆向 + 动静态分析 + 自动化验证 + 批量 APP 输出”
- **当前缺口**：
  - 缺少统一证据模型（policy/static/dynamic/network 未结构化对齐）
  - 缺少“同意关闭后再验证”的状态机测试
  - 缺少“访问副本完整性”自动比对与可解释报告

结论：你的思路方向正确，关键是从“LLM 主导判断”转为“证据主导判断，LLM 辅助”。

---

## 3. 落地技术路线（核心原则）

1. **证据优先**：最终结论必须可追溯到 policy 文本、静态 API、Frida 日志、网络证据  
2. **LLM 退居二线**：只用于补全和推荐，不参与最终 pass/fail  
3. **先最小闭环，再扩展**：先跑通 3 个 APP + 2 类个人信息，再扩展到 >=10 个 APP  
4. **彻底去历史包袱**：不与 `oldsrc` 兼容，避免技术债延续

## 4. 逐过程开发方案（可执行）

## 阶段 0：基线冻结与实验对齐（0.5 天）

- **输入**：Lab4 要求、样本 APP 列表、隐私政策文本
- **动作**：
  - 定义统一数据模型：`EvidenceItem`、`RightClaim`、`VerificationResult`
  - 明确 MVP 范围：先覆盖 Lab4-1，再扩展 Lab4-2/Lab4-3
- **输出**：
  - `docs/schema.md`
  - `config/personal_info.yaml` 初版字段规范
- **验收标准**：
  - 每条结论可对应至少 1 条可落地证据字段（不是自然语言描述）

## 阶段 1：知识库与规则引擎（1 天）

- **输入**：个人信息定义、法规关键词、现有分类标签
- **动作**：
  - 新建 `personal_info.yaml`（aliases/permissions/apis/hooks/network_keys）
  - 新建 `rules/decision_rules.yaml`，定义判定矩阵：
    - `declared + observed` => 一致
    - `not_declared + observed` => 高风险不一致
    - `declared + not_observed` => 待验证/弱证据
  - 将旧分类标签映射到新 schema
- **输出**：
  - 可被程序读取的规则文件
- **验收标准**：
  - 不调用 LLM 时可独立完成初步判定

## 阶段 2：静态分析接入（Exodus + Androguard）（1~1.5 天）

- **输入**：APK 列表（先 3 个样本）
- **动作**：
  - 写 `exodus_adapter.py`：提取权限、tracker、风险组件
  - 写 `androguard_scanner.py`：提取与个人信息相关 API 命中及调用上下文
  - 输出标准化 `static_evidence.json`
- **输出**：
  - 每 APP 一份静态证据文件
- **验收标准**：
  - 个人信息项至少能定位到 `permission` 或 `api` 其中之一

## 阶段 3：动态取证改造（Appium + Frida）（2 天）

- **输入**：阶段 2 候选信息项、新设计的 Appium 测试路径
- **动作**：
  - 在 `src` 新实现 Appium 执行层，并新增 Frida 注入执行层 `frida_runner.py`
  - 建立 hooks 注册机制（按个人信息类型自动加载脚本）
  - 输出 `dynamic_evidence.json`：记录时间戳、调用栈摘要、参数摘要、截图路径
  - 将 LLMVerifier 从“裁决器”改成“路径建议器/解释器”
- **输出**：
  - 同步生成 UI 测试结果 + Frida 证据
- **验收标准**：
  - 至少 2 类个人信息可稳定抓到运行时证据（多次重复一致）

## 阶段 4：Lab4-1 知情权闭环（1 天）

- **输入**：policy claims + static + dynamic evidence
- **动作**：
  - `policy_parser.py` 输出“声明获取项”
  - `compare_engine.py` 按规则自动判定真实性等级（一致/疑似不一致/不一致）
  - 报告中展示“声明-静态-动态”三联证据链
- **输出**：
  - `lab4_1_result.json`、可视化报告（md/html/xlsx 任选一种主格式）
- **验收标准**：
  - 任意一个结论都可在报告中点击或定位到具体证据记录

## 阶段 5：Lab4-2 同意权真实性（1 天）

- **输入**：可关闭项（开关、权限、功能入口）
- **动作**：
  - 设计开关前后 A/B 用例：`before_off` vs `after_off`
  - 同一路径重复执行动态取证，对比采集事件差异
  - 识别“表面关闭但仍采集”场景
- **输出**：
  - `lab4_2_result.json`（含开关行为证据）
- **验收标准**：
  - 每个可关闭项至少一组前后对照证据

## 阶段 6：Lab4-3 访问权真实性（1~1.5 天）

- **输入**：Lab3 中副本导出路径与副本文件
- **动作**：
  - Appium 自动触发副本申请/导出流程
  - 将副本字段与动态取证字段做自动比对（完整性检查）
  - 增加“是否存在上行发送路径”的静态辅助判断（网络 API/域名线索）
- **输出**：
  - `lab4_3_result.json`、副本完整性评分
- **验收标准**：
  - 至少输出：已声明字段数、运行时观测字段数、副本覆盖字段数、缺失字段清单

## 阶段 7：批量化与验收交付（1 天）

- **输入**：>=10 个 APP 测试清单
- **动作**：
  - 跑批调度（失败重试、断点续跑、日志归档）
  - 统一输出按 APP 汇总的总表 + 每 APP 证据包
  - 生成课堂汇报素材图表（按实验维度组织，不再仅展示模型分数）
- **输出**：
  - 总报告、附录证据包、可复现实验命令清单
- **验收标准**：
  - 不少于 10 个 APP；每个 APP 有结构化结论与证据路径

## 7. 关键风险与回退策略

- **风险 1：Frida 在部分 APP 上对抗严重**
  - 回退：优先保留 Appium + 静态证据，动态层至少覆盖核心样本 APP
- **风险 2：UI 自动化路径脆弱**
  - 回退：将路径脚本化 + 屏幕关键字锚点，多策略匹配并保留人工复核入口
- **风险 3：LLM 不稳定影响结果一致性**
  - 回退：LLM 不参与最终判定；仅用于提示与解释文案生成
- **风险 4：时间不足无法全覆盖**
  - 回退：先保障 Lab4-1 全量 + Lab4-2/3 代表性样本，报告中明确覆盖边界

你的开源接入方向是正确的，且与 Lab4 要求高度一致。真正决定成败的不是“再换一个更强模型”，而是把系统改造成**证据链驱动**：规则可复现、结果可解释、流程可批量。
