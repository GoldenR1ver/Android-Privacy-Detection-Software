# 安卓隐私检测程序开发计划（Lab4 落地版）

## 1. 任务理解与目标

你当前已经有一条实验性管线（`oldsrc`），覆盖了：
- 隐私政策文本读取与句子级分类（知情权、决定权、访问权、修改权、删除权）
- 聚类分析
- 权限/路径判断
- 基于 Appium + MuMu 的动态执行
- LLM（`deepseek-chat`）参与大量判断

本次目标是**完全弃用 `oldsrc`，在 `src` 下重建一条可复现、可解释、可批量跑 >=10 个 APP** 的工程化工具，并对齐 Lab4 的三项核心评估：
- Lab4-1：知情权真实性（声明 vs 实际获取）
- Lab4-2：同意权真实性（关闭是否真的生效）
- Lab4-3：访问权真实性（副本完整性 + 实际采集与传输）

---

## 2. 可行性评估（结论：可行，建议全新分层重构）

## 2.1 现有方案可借鉴程度（不复用代码）

- **可复用的是“设计思想”，不是实现代码**
  - 保留流程思想：政策声明 -> 静态证据 -> 动态证据 -> 比对判定 -> 报告
  - 保留输出思想：按 APP 生成结构化结果与证据包
- **全部代码在 `src` 重写**
  - 避免旧代码中的实验性依赖与耦合关系继续扩散
  - 统一命名、统一数据结构、统一 CLI，降低后期维护成本

## 2.2 与开源组件结合的可行性

- **Exodus**：适合做 APK 初筛（权限、tracker、SDK 风险）  
  可行，接入成本低，适合作为“风险候选生成器”
- **Androguard**：适合做静态 API/调用证据提取  
  可行，能给出比 LLM 更稳定的“代码证据”
- **Frida（含 hooks 模板）**：适合做运行时 **Java API** 运行时取证  
  可行，但受模拟器/商业 APP 限制大（见第 10、16 节）；**不能作为唯一动态轨**
- **TrackerControl**（`utils/tracker-control-android`）：本地 VPN + tracker 域名库 + DEX 签名扫描  
  **高度可行**，补「网络外传 / SDK 嵌入」证据，**不依赖 Java 桥**；借鉴其 blocklist 与 `TrackerLibraryAnalyser` 思路，不必移植整套 VPN App
- **PrivacyMonitorAndroid**（`utils/PrivacyMonitorAndroid`）：Gradle ASM 编译期插桩 + 堆栈 + Excel  
  **部分可行**：API 清单与证据格式可直接借鉴；**部署方式不可用于第三方 APK**（需源码重编译），运行时等价物为本项目 `hook_papi.js` + `personal_info.yaml`

## 2.3 与 Lab4 要求匹配度

- **匹配度高**：实验强调“逆向 + 动静态分析 + 自动化验证 + 批量 APP 输出”
- **当前缺口**：
  - 缺少统一证据模型（policy/static/dynamic/network 未结构化对齐）
  - 缺少“同意关闭后再验证”的状态机测试
  - 缺少“访问副本完整性”自动比对与可解释报告

结论：你的思路方向正确，关键是从“LLM 主导判断”转为“证据主导判断，LLM 辅助”。

---

## 3. 落地技术路线（核心原则）

1. **证据优先**：最终结论必须可追溯到 policy 文本、静态 API、Frida 日志、网络证据  
2. **多轨动态、按能力选轨**（借鉴 TrackerControl）：Frida Java 失败时自动降级到 **网络轨 / 静态 tracker 轨 / UI 轨**，禁止「单轨失败 = 实验失败」  
3. **声明式 API 清单**（借鉴 PrivacyMonitorAndroid）：所有监控点收敛到 `personal_info.yaml` + `privacy_trace_methods.txt`，报告统一「API + 堆栈 + 政策」三列  
4. **LLM 退居二线**：只用于补全和推荐，不参与最终 pass/fail  
5. **先最小闭环，再扩展**：先跑通 3 个 APP + 2 类个人信息，再扩展到 >=10 个 APP  
6. **彻底去历史包袱**：不与 `oldsrc` 兼容，避免技术债延续

## 4. 逐过程开发方案（可执行）

## 阶段 0：基线冻结与实验对齐（0.5 天）

- **输入**：Lab4 要求、样本 APP 列表、隐私政策文本
- **动作**：
  - 定义统一数据模型：`EvidenceItem`、`RightClaim`、`VerificationResult`
  - 明确 MVP 范围：先覆盖 Lab4-1，再扩展 Lab4-2/Lab4-3
- **输出**：
  - `docs/schema.md`
  - `config/personal_info.yaml` 初版字段规范
- **验收标准**：
  - 每条结论可对应至少 1 条可落地证据字段（不是自然语言描述）

## 阶段 1：知识库与规则引擎（1 天）

- **输入**：个人信息定义、法规关键词、现有分类标签
- **动作**：
  - 新建 `personal_info.yaml`（aliases/permissions/apis/hooks/network_keys）
  - 新建 `rules/decision_rules.yaml`，定义判定矩阵：
    - `declared + observed` => 一致
    - `not_declared + observed` => 高风险不一致
    - `declared + not_observed` => 待验证/弱证据
  - 将旧分类标签映射到新 schema
- **输出**：
  - 可被程序读取的规则文件
- **验收标准**：
  - 不调用 LLM 时可独立完成初步判定

## 阶段 2：静态分析接入（Exodus + Androguard）（1~1.5 天）

- **输入**：APK 列表（先 3 个样本）
- **动作**：
  - 写 `exodus_adapter.py`：提取权限、tracker、风险组件
  - 写 `androguard_scanner.py`：提取与个人信息相关 API 命中及调用上下文
  - 输出标准化 `static_evidence.json`
- **输出**：
  - 每 APP 一份静态证据文件
- **验收标准**：
  - 个人信息项至少能定位到 `permission` 或 `api` 其中之一

## 阶段 3：动态取证改造（Appium + Frida）（2 天）

- **输入**：阶段 2 候选信息项、新设计的 Appium 测试路径
- **动作**：
  - 在 `src` 新实现 Appium 执行层，并新增 Frida 注入执行层 `frida_runner.py`
  - 建立 hooks 注册机制（按个人信息类型自动加载脚本）
  - 输出 `dynamic_evidence.json`：记录时间戳、调用栈摘要、参数摘要、截图路径
  - 将 LLMVerifier 从“裁决器”改成“路径建议器/解释器”
- **输出**：
  - 同步生成 UI 测试结果 + Frida 证据
- **验收标准**：
  - 至少 2 类个人信息可稳定抓到运行时证据（多次重复一致）

## 阶段 4：Lab4-1 知情权闭环（1 天）

- **输入**：policy claims + static + dynamic evidence
- **动作**：
  - `policy_parser.py` 输出“声明获取项”
  - `compare_engine.py` 按规则自动判定真实性等级（一致/疑似不一致/不一致）
  - 报告中展示“声明-静态-动态”三联证据链
- **输出**：
  - `lab4_1_result.json`、可视化报告（md/html/xlsx 任选一种主格式）
- **验收标准**：
  - 任意一个结论都可在报告中点击或定位到具体证据记录

## 阶段 5：Lab4-2 同意权真实性（1 天）

- **输入**：可关闭项（开关、权限、功能入口）
- **动作**：
  - 设计开关前后 A/B 用例：`before_off` vs `after_off`
  - 同一路径重复执行动态取证，对比采集事件差异
  - 识别“表面关闭但仍采集”场景
- **输出**：
  - `lab4_2_result.json`（含开关行为证据）
- **验收标准**：
  - 每个可关闭项至少一组前后对照证据

## 阶段 6：Lab4-3 访问权真实性（1~1.5 天）

- **输入**：Lab3 中副本导出路径与副本文件
- **动作**：
  - Appium 自动触发副本申请/导出流程
  - 将副本字段与动态取证字段做自动比对（完整性检查）
  - 增加“是否存在上行发送路径”的静态辅助判断（网络 API/域名线索）
- **输出**：
  - `lab4_3_result.json`、副本完整性评分
- **验收标准**：
  - 至少输出：已声明字段数、运行时观测字段数、副本覆盖字段数、缺失字段清单

## 阶段 7：批量化与验收交付（1 天）

- **输入**：>=10 个 APP 测试清单
- **动作**：
  - 跑批调度（失败重试、断点续跑、日志归档）
  - 统一输出按 APP 汇总的总表 + 每 APP 证据包
  - 生成课堂汇报素材图表（按实验维度组织，不再仅展示模型分数）
- **输出**：
  - 总报告、附录证据包、可复现实验命令清单
- **验收标准**：
  - 不少于 10 个 APP；每个 APP 有结构化结论与证据路径

## 7. 关键风险与回退策略

- **风险 1：Frida 在部分 APP 上对抗严重**
  - 回退：优先保留 Appium + 静态证据，动态层至少覆盖核心样本 APP

  - 回退：将路径脚本化 + 屏幕关键字锚点，多策略匹配并保留人工复核入口
- **风险 3：LLM 不稳定影响结果一致性**
  - 回退：LLM 不参与最终判定；仅用于提示与解释文案生成
- **风险 4：时间不足无法全覆盖**
  - 回退：先保障 Lab4-1 全量 + Lab4-2/3 代表性样本，报告中明确覆盖边界

### 10.2 原设计 vs 实际落地

```text
设计链路：政策声明 → 静态 APK → Appium 触发 → Frida+PAPI Hook → OkHttp 污点 → 规则比对

实际状态：
  Lab4-1  A→B→F  ✓  闭环已通，可批量 10 APP
  Lab4-2  C      △  UI 多数可跑，强防护 APP 导航不完整
  Lab4-2  D→E    ✗  代码齐全，真机几乎无 runtime 事件
  Lab4-3         △  管线有，副本人工收集为主
```

**一句话结论**：Lab4-1 靠静态 + 政策可做好；Lab4-2 依赖的运行时 Frida 证据被「商业 APP 反 Frida + attach 时机 + 进程选错 + Hook 点与真实路径不一致 + 部分批次 dry_run 污染」共同击穿。与其他组经验一致：**多数大厂 APP Frida 难绕过，需筛选可注入子集并诚实划定覆盖边界。**

### 10.3 真机 Frida 失败分类（`stage3_dynamic_real`）

| 失败类型 | 代表 APP | 典型 `frida_result.error` |
|----------|----------|---------------------------|
| 反注入 / agent 拒绝 | Keep、支付宝 | `refused to load frida-agent`、`java_not_ready` |
| 进程瞬杀 | 东方财富 | `unable to write to process memory: No such process` |
| 找不到进程 | 小红书、58同城、智联招聘 | `no process found`（Appium 结束后进程已退出） |
| 连接断开 | LOFTER | `the connection is closed` |
| 注入成功但 0 事件 | 小荷健康、世纪佳缘 | attach 成功、`papi_installed_accepted>0`，仅 `hook_loaded` 无 API 调用 |

### 10.4 已发现的工程缺陷（须优先修复）

1. **PAPI 异步安装被当作同步**：`hook_papi.js` 的 `installhooks` 在 `Java.perform` 完成前即返回 `spec.length`；Appium 可能在 hook 真正装上之前就开始操作。
2. **Lab4-2 批跑默认关闭 Frida**：`run_lab42_ui_batch.py` 仅 `--real-run`，未加 `--enable-frida`；after 阶段产生 `mode: dry_run` + `frida_disabled` 的模拟事件，会导致 Lab4-2 出现虚假的 `after_runtime_hits`（如 Keep after=19 实为 dry_run）。
3. **attach 模式漏采冷启动**：IMEI / Android ID 常在 `Application.onCreate` 或 SDK 初始化时读取，attach 晚于首次采集窗口。
4. **Lab4-2 无法区分「未观测」与「开关无效」**：before=0、after=0 时 `comparisons` 为空，无法支撑同意权结论。

## 11. Lab4-2 提升策略（同意权真实性）

### 11.1 总体原则

- **不与大厂硬刚 Frida**：Lab4-2 的 Frida A/B 仅在「可注入 Tier」上产出强结论；其余 APP 走 UI 轨 + 静态辅助。
- **before/after 必须同轨同质**：同一 APP 的两次采集必须同为 `mode: real` 且 `enable_frida` 一致，禁止 dry_run 进入 `lab4_2_pipeline`。
- **延长观测窗口**：标识符读取与网络上报具有异步性，默认 grace/tail 过短。

### 11.2 策略 A：建立 Frida 友好 APP 分层（最高优先级）

| 层级 | 特征 | 当前线索 | Lab4-2 用途 |
|------|------|----------|-------------|
| **Tier-1 可注入** | attach 成功、无 agent 拒绝 | 小荷健康、世纪佳缘（需补 runtime） | Frida before/after A/B 主攻 |
| **Tier-2 弱防护** | 中小工具、地方服务类 | 课程样本库另选 2~3 个 | 扩展 Frida 样例 |
| **Tier-3 强防护** | 金融、头部大厂 | 支付宝、Keep | **仅 UI + 静态**，不写 Frida 同意权结论 |

**操作清单**：

## 12. 安卓隐私工程视角：采集、通信、防护与分析

> 本节从 **Android 应用开发实现** 出发，说明隐私数据在代码里「在哪产生、如何流动、如何被保护、检测工具应对准哪里」。与 `personal_info.yaml` 的 `permissions / apis / api_targets / network_keys` 字段一一对应。

### 12.1 隐私数据在 Android 中的典型触点

```text
┌─────────────────────────────────────────────────────────────────┐
│                        Android 应用进程                          │
├──────────────┬──────────────┬──────────────┬────────────────────┤
│  采集层       │  存储层       │  加工层       │  外传层             │
│  Sensor      │  SharedPref  │  加密/哈希    │  HTTP(S)/SDK       │
│  LocationMgr │  SQLite/Room │  JSON 组装    │  Binder/AIDL       │
│  Telephony   │  文件/缓存    │  埋点队列     │  WebView/JSBridge  │
│  ContentProv │  Keystore    │  画像/推荐    │  推送/广告 SDK      │
│  Clipboard   │  AccountMgr  │              │  深链/分享          │
└──────────────┴──────────────┴──────────────┴────────────────────┘
         ↑              ↑              ↑              ↑
    运行时 Hook     静态权限+路径    业务逻辑       网络 Hook / mitm
```

| 类别 | 开发侧常见实现 | 对应 Android 机制 | 本项目中检测手段 |
|------|----------------|-------------------|------------------|
| **设备标识** | `TelephonyManager.getImei`、`Settings.Secure.ANDROID_ID`、OAID SDK | 系统 API + 厂商 SDK | `hook_papi.js` + `hook_oaid.js`；静态扫 SDK 包名 |
| **位置** | `FusedLocationProvider`、`LocationManager`、Wi‑Fi/基站辅助 | 运行时权限 `ACCESS_FINE_LOCATION` | `hook_location.js`；UI 触发定位相关页面 |
| **通讯录/日历** | `ContentResolver.query(ContactsContract...)` | `READ_CONTACTS` 等 | PAPI `ContentResolver.query`；注意 query URI 过滤 |
| **剪贴板** | `ClipboardManager.getPrimaryClip` | 无独立权限（高版本有 toast 提示） | `hook_clipboard.js` |
| **账号与画像** | 登录态 Token、用户填写的资料 | 应用私有存储 + 服务端会话 | UI 导航至「个人资料」；副本字段比对（Lab4-3） |
| **行为日志** | 埋点 SDK（友盟、GrowingIO 等） | 批量上报、可能含设备指纹 | 静态 Exodus tracker；OkHttp hook；mitm |
| **生物特征** | `BiometricPrompt`、人脸/指纹仅本地校验 | 通常不上传原始生物数据 | 静态 API + 政策声明核对 |
| **跨应用标识** | 广告 ID、OAID、自定义 `device_id` | Google Play Services / 移动联盟 | OAID hook；`network_keys` 在 body 中匹配 |

**Android 版本约束（检测时必须考虑）**：

- **Android 10+**：普通应用无法读取 IMEI；开发者转向 OAID、Android ID、广告 ID、安装列表等。
- **Android 11+**：包可见性限制，`queryIntentActivities` 等行为变化；部分采集改走 SDK 或服务器下发。
- **Android 13+**：通知、媒体、附近 Wi‑Fi 等权限细粒度化；政策声明需与 `targetSdk` 一致。

### 12.2 隐私内容如何通信（外传路径）

开发侧常见外传拓扑：

```text
[App 业务代码]
    → [统一网络层封装 Retrofit/OkHttp/Volley]
    → [可选：SDK 内部 HTTP / Native libcurl]
    → TLS 加密
    → 自有后端 api.xxx.com
    → 或第三方：广告(ad.xxx)、统计(log.xxx)、推送、地图、风控

[WebView H5]
    → JavaScript 调 AndroidInterface / @JavascriptInterface
    → 同样进入上述网络层

[系统分享/深链]
    → Intent 携带 Uri（可能含用户生成内容）
```

| 通信形态 | 开发实现要点 | 检测 Implication |
|----------|--------------|------------------|
| **JSON REST** | `RequestBody` 含 `deviceId`、`userId`、`lat` | OkHttp hook 解析 body；`network_keys` 子串匹配 |
| **Protobuf / 二进制** | 埋点常用，body 不可读 | 静态找 SDK；mitm 看域名与流量大小；Frida hook SDK 入口类 |
| **HTTPS + 证书锁定** | `CertificatePinner`、自定义 TrustManager | mitm 需 patch 或 Frida 绕过 pinning；实验可优先选未 pin 的 Tier-1 APP |
| **多进程** | `:push`、`:webview` 子进程上报 | 须 attach **含网络栈的进程**；MuMu 上父/子 PID 易错 |
| **延迟/批量上报** | 队列 + 后台 Job / WorkManager | 采集窗口需 tail 足够长；关闭开关后仍可能有缓存上报 |
| **邮箱副本（Lab4-3）** | 服务端异步生成 ZIP/链接发邮件 | 无法被 Frida 直接观测「发了什么给邮箱」；靠副本文件与运行时字段交叉验证 |

**污点分析（taint）在 Android 上的现实含义**：

- 学术意义上的「源→汇」追踪在 Java 层可用 Frida 做 **近似**：Hook 标识符读取 API（源）与 `OutputStream.write` / `OkHttp.RequestBody`（汇），比对时间窗与调用栈。
- 本项目 `hook_network_okhttp.js` + `hook_papi.js` 即 **轻量污点链**：同一会话内若先 `getImei` 后 `OkHttp.execute` 且 body 含 `imei`，可记为传播证据；**不能**在强混淆 + 反 Frida 场景下保证完备。

### 12.3 应用如何防止注入与调试（反 Frida / 反分析）

商业 APP 从开发角度常用的防护栈（也是本实验失败的主要原因）：

| 层级 | 典型实现 | 检测/绕过思路（实验级） |
|------|----------|-------------------------|
| **Native 检测** | `fopen("/proc/self/maps")` 搜 `frida`/`gum-js`；`pthread_create` 轮询 | 改名 frida-server、hide maps；真机 Magisk + Shamiko |
| **Java 检测** | 异常线程数、类加载器校验、`Debug.isDebuggerConnected` | spawn 早于检测初始化；hook 检测函数返回 false |
| **完整性校验** | APK 签名、DEX CRC、SO 校验 | 重打包会触发；动态分析尽量不重打包 |
| **ptrace 占坑** | 子进程 anti-attach | 选用无 ptrace 的 APP；spawn 模式 |
| **多进程守护** | 主进程崩溃则重启；注入错进程 | `pidof` + Frida `enumerate_processes` 消歧（已实现于 `frida_runner.py`） |
| **SSL Pinning** | OkHttp `CertificatePinner` | objection/mitm 专用脚本；或只分析未 pin 的 Tier-1 |
| **混淆/R8** | 类名 `a.b.c`，方法名保留 | `hook_network_okhttp.js` 的 RealCall 指纹发现；Androguard 扫字符串常量 |
| **风控 SDK** | 阿里聚安全、腾讯乐固、梆梆等 | 一体加固后 Frida 极难；**避开或仅静态** |

**对本项目的指导意义**：

- **不要假设** `TelephonyManager.getImei` hook 能代表「设备信息采集」；大厂 APP 多走 **SDK + Native + 服务端下发配置**。
- **attach 成功 ≠ 业务逻辑进程**：MuMu 上显示名「Keep」的进程可能是壳，真正 ART 业务在子进程且拒绝注入。
- **检测工具应分层**：静态（必做）→ UI（必做）→ Frida（Tier-1）→ mitm（可选）→ 人工副本（Lab4-3）。

### 12.4 从开发视角如何做隐私合规（与检测对称）

应用侧合规实现（检测工具要找的「应有行为」）：

| 合规要求 | 开发常见做法 | 检测映射 |
|----------|--------------|----------|
| 知情同意 | 首次启动隐私弹窗、`PrivacyPolicyActivity` | 政策文本 `declared_pii`；UI 是否出现弹窗（截图） |
| 最小必要 | 按功能申请权限，拒绝后降级 | Appium 拒绝权限后功能是否可用；Frida 是否仍调用 API |
| 可撤回同意 | 设置页开关、撤回授权、基本功能模式 | **Lab4-2 核心**：开关前后 API/网络上报对比 |
| 访问权 | 个人信息下载、副本导出 | **Lab4-3**：`user_copy_normalized` vs `observed_pii` |
| 第三方共享清单 | 隐私政策列举 SDK | Exodus tracker vs 实际上报域名 |

## 13. 软件 — 政策 — 用户行为 映射模型

> 本项目的 `compare_engine` 本质是在三张图上做 **节点对齐**：政策声明了什么、代码能做什么、用户操作后实际发生了什么。

### 13.1 三张图

```text
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  政策图 (Policy)  │     │  软件图 (Software)│     │ 行为图 (Behavior) │
│  隐私政策文本      │     │  Manifest 权限    │     │  Appium 导航路径   │
│  declared_pii    │     │  静态 API/SDK     │     │  开关 tap 步骤     │
│  法条关键词        │     │  Hook 点/网络汇    │     │  权限 grant/deny   │
└────────┬─────────┘     └────────┬─────────┘     └────────┬─────────┘
         │                        │                        │
         └────────────────────────┼────────────────────────┘
                                  ▼
                    ┌─────────────────────────┐
                    │  证据融合 + 规则判定       │
                    │  lab4_1 / lab4_2 / lab4_3│
                    └─────────────────────────┘
```

### 13.2 映射关系表（Lab4 三维）

| Lab | 政策侧（声明） | 软件侧（能力/实现） | 用户行为侧（触发/选择） | 判定问题 |
|-----|----------------|---------------------|-------------------------|----------|
| **Lab4-1 知情权** | `policy_parser` → `declared_pii` | 静态 `permissions`+`apis`；动态 `observed_pii` | UI 是否进入需采集的页面（辅助） | 声明了但没做？没声明但做了？ |
| **Lab4-2 同意权** | 政策中「可关闭」「撤回授权」「基本功能模式」句子 | 设置页开关对应的 **客户端逻辑分支**（理想：关闭后不调 API） | before：开关 ON + 正常浏览；after：用户手动关开关 + 同路径浏览 | 关闭后 Frida 仍命中？UI 仍显示「已开启」？网络上报仍在？ |

### 13.3 用户行为 → 软件观测 的因果链（Lab4-2 设计依据）

```text
用户操作                    预期软件响应                      取证点
─────────────────────────────────────────────────────────────────────
首次安装，点「同意」         初始化 SDK，可能读 Android ID      spawn + 短窗口 Frida
进入需定位的功能             申请 LOCATION 权限                 权限对话框 + getLastKnownLocation
关闭「个性化推荐」           停止推荐算法用的画像上报            Frida: 定位/ID API 减少；mitm: 推荐域名流量减少
关闭「基本功能模式」         停止非必要采集                      同上；UI: 基本版页面 keyword
撤回 READ_CONTACTS          ContentResolver 不再 query 通讯录    hook_contacts / PAPI query
申请个人信息副本             服务端聚合字段 → 导出文件           副本 JSON vs observed_pii
```

**关键认识**：用户行为是 **实验自变量**；Frida/network 是 **因变量观测**；政策是 **期望函数**（声明在开关关闭后应停止何种处理）。三者不对齐时，才产生 `inconsistent_high_risk` / `still_collecting_after_off` 等 verdict。

### 13.4 `personal_info.yaml` 作为三张图的枢纽

每个 `pii_type` 条目应维护跨图链接（与当前 schema 对齐，可逐步补全）：

```yaml
# 示例：contact_list 在三图中的锚点
contact_list:
  policy_keywords: ["通讯录", "联系人"]      # → 政策图
  permissions: ["READ_CONTACTS"]            # → 软件图（Manifest）
  apis: ["ContactsContract", "query"]     # → 软件图（静态）
  api_targets: [{ clazz: android.content.ContentResolver, method: query }]  # → 软件图（动态）
  hooks: ["hook_contacts.js"]               # → 行为触发后的观测
  network_keys: ["contacts", "contact_phone"]  # → 外传图
  related_rights: ["informed", "consent", "access", "deletion"]
```

Lab4-1 对齐 **政策图 ↔ 软件图**；Lab4-2 对齐 **政策承诺 ↔ 行为干预后的软件图**；Lab4-3 对齐 **政策图 ↔ 副本图 ↔ 软件图（运行时）**。

## 16. 开源借鉴落地路线图（TrackerControl + PrivacyMonitorAndroid）

> 参考仓库路径：`project/utils/tracker-control-android`、`project/utils/PrivacyMonitorAndroid`  
> 目标：在**不移植整套 Android App** 的前提下，把可复用思想落到 `src/privacy_audit`，形成**切实可跑**的多轨检测程序。

### 16.1 两个仓库的借鉴边界

| 仓库 | 核心能力 | 能否直接接入第三方 APK | 本项目落地方式 |
|------|----------|------------------------|----------------|
| **TrackerControl** | 设备内 VPN 记录流量元数据；tracker 域名库；DEX 扫 SDK 签名（Exodus/ClassyShark） | VPN 分析**可以**（不需改 APK） | Python 侧：静态 DEX 扫描 + mitm/流量日志解析 + 域名对照 |
| **PrivacyMonitorAndroid** | 编译期 ASM 对 `-tracemethod` 插桩；`PrivacyCollect` 记堆栈；导出 Excel | **不能**（必须源码 + Rebuild） | 配置格式与报告列对齐；运行时由 Frida `hook_papi.js` 承担插桩语义 |

**当前真机/MuMu 诊断结论**（钓鱼人 `probe_hook --java-wait-only`）：

- `script_loaded` ✓ → 注入与消息通道正常  
- `java_never_ready` ✗ → **Java API 轨不可用**  
- 因此：**第 16 节网络轨 + 静态 tracker 轨是「切实可用」的主线补充**，而非可选项。

### 16.3 阶段 R1：PrivacyMonitorAndroid 式「声明式 API + 堆栈报告」（1~1.5 天）

**借鉴点**：`privacyTraceConfig.txt`、`TraceClassVisitor`、`PrivacyCollect.appendData`。

| 任务 | 文件 | 动作 |
|------|------|------|
| R1.1 统一监控清单 | `input/privacy_trace_methods.txt` | 从 PMA 格式迁移：`-tracemethod android/provider/Settings$Secure.getString`；与 `personal_info.yaml` 的 `api_targets` 双向同步 |
| R1.2 生成 hook spec | `scripts/sync_trace_config.py` | 读取 txt → 生成/校验 `personal_info.yaml` 的 `api_targets` 与 `hook_papi` spec |
| R1.3 强化堆栈 | `hooks/hook_papi.js` + 各 `hook_*.js` | 保证每条 runtime 事件带 `stack_summary`（PMA 的 `getStackTrace()` 等价） |
| R1.4 Excel 报告 | `reporting/excel_writer.py` | 列：`app_name \| pii_type \| api_name \| stack_summary \| declared_in_policy \| evidence_level` |
| R1.5 探针入库 | `scripts/probe_hook.py` 结果 | 将 `java_bridge_ok / java_never_ready` 写入 `output/frida_probe/<app>.json`，供 tier 与批跑读取 |

**验收**：

- 对至少 1 个 Tier-1 APP，Excel 中能展开「哪条隐私 API、哪条堆栈、政策是否声明」
- 对 `java_never_ready` APP，报告仍能通过静态+UI 出 Lab4-1，不空白

### 16.4 阶段 R2：TrackerControl 式「静态 Tracker / SDK 扫描」（1.5~2 天）

**借鉴点**：`TrackerLibraryAnalyser.java`、`trackers.json`、`ExodusTracker`。

| 任务 | 文件 | 动作 |
|------|------|------|
| R2.1 精简 tracker 库 | `input/tracker_blocklist/` | 从 TC `app/src/main/assets/trackers.json` 提取域名+公司+目的字段，或对接 Exodus API 结果 |
| R2.2 DEX 签名扫描 | `analyzers/static/tracker_dex_scanner.py` | 用 androguard/dex 遍历类名，匹配 tracker 库中的 SDK 包名前缀（逻辑参考 `TrackerLibraryAnalyser`） |
| R2.3 并入 stage2 | `workflows/stage2_static_pipeline.py` | `static_evidence.json` 增加 `embedded_trackers: [{name, category, signatures[]}]` |
| R2.4 Lab4-1 比对 | `compare_engine.py` | 政策「第三方 SDK 共享」章节 vs `embedded_trackers`；未声明但嵌入 → `inconsistent_high_risk`（S1 级） |

**验收**：

- Lab4-1 报告有「声明 SDK vs 静态嵌入」对照表

### 16.5 阶段 R3：TrackerControl 式「网络动态轨」（2~3 天，Frida 失败时的主替代）

**借鉴点**：TC 论文「on-device 网络分析」；不移植 NetGuard VPN，用 **mitmproxy + 域名规则** 达到同等证据粒度。

| 任务 | 文件 | 动作 |
|------|------|------|
| R3.1 流量采集 | `analyzers/network/mitm_runner.py` | 启动 mitmproxy；MuMu 安装用户证书；stage3 期间记录 `host, path, timestamp` |
| R3.2 域名匹配 | `analyzers/network/tracker_matcher.py` | 请求 host 对照 `tracker_blocklist`；输出 `network_evidence.json`：`{tracker_company, purpose, host}` |
| R3.3 PII 关键字 | `personal_info.yaml` 的 `network_keys` | body/query 子串匹配 `device_id`, `oaid`, `android_id` 等（TC + 本项目已有字段） |

**验收**：

- 钓鱼人：无 Frida runtime，但 mitm 能记录 ≥1 条外连域名，并对照 tracker 库给出公司名
- Lab4-2 至少 1 个 APP 具备「轨 3：关闭开关前后网络对比」（见 11.5 节）

**注意**：HTTPS + 证书锁定 APP 可能 mitm 失败，报告中标注 `mitm_blocked: pinning` 并回退到静态 tracker 轨。
